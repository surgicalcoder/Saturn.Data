# SourceCodeGenerator.cs — Change-Detection & Scope-Removal Assessment

Scope: `Saturn.Generator.Entities/SourceCodeGenerator.cs` (`GoLive.Saturn.Generator.Entities.SourceCodeGenerator`).
Reference bases verified against `Saturn.Data.Entities/GoLive.Saturn.Data.Entities/Entity.cs`, `MultiscopedEntity.cs`, `SecondScopedEntity.cs`, `ScopedEntity.cs`, `Ref.cs`, plus `Scanner.cs` and `MemberToGenerate.cs`.

## 1. Change Detection

### 1.1 How it works today

Every non-collection property setter generated by `GenerateNormalMember` ultimately calls `Entity.SetField<T>` (`Entity.cs:233`):

```csharp
protected virtual bool SetField<T>(ref T field, T newValue, [CallerMemberName] string propertyName = null)
{
    if (!EqualityComparer<T>.Default.Equals(field, newValue))
    {
        field = newValue;
        if (propertyName != null && Changes != null && EnableChangeTracking)
            Changes[propertyName] = newValue;
        OnPropertyChanged(propertyName);
        return true;
    }
    return false;
}
```

`Changes` is `Dictionary<string, object>` keyed by property name; `EnableChangeTracking` is a manual toggle. So "change detection" = "while tracking is on, record the latest value written to each property". No baseline, no diff, no history.

### 1.2 Findings

**A. `[DoNotTrackChanges]` is misnamed — it skips generation entirely, not tracking.**
`Scanner.cs:341-344`:
```csharp
if (AttributeExists(attr, ATTRIBUTES_DoNotTrackChanges))
    continue;
```
The member is dropped from `MemberToGenerate` entirely → no property is emitted at all. A user reading `DoNotTrackChanges` reasonably expects the property to exist but be excluded from `Changes`. Either rename to `[ExcludeFromGeneration]` or split into two attributes. Current behavior is a footgun.

**B. Collection change tracking is fundamentally broken for anything but sequential Add.**
Generated ctor hook (`SourceCodeGenerator.cs:60`):
```csharp
{coll}.CollectionChanged += (in NotifyCollectionChangedEventArgs<T> eventArgs) =>
    Changes.Upsert($"{collTargetName}.{eventArgs.NewStartingIndex}", eventArgs.NewItem);
```

Defects:
1. **Remove / Replace / Move / Reset unhandled.** `NewStartingIndex` is `-1` for Reset and typically for Move; for Remove, `NewItem` is `default` → writes `null` at the removed index (silent corruption). For Replace it writes the new item but never clears the old key intent.
2. **Index-based keys collide.** Add at index 0 twice → second overwrites first → silent data loss. Indices shift on insert/remove, so a positional key cannot represent identity.
3. **No `EnableChangeTracking` gate.** Property setters honor the toggle; collection handler does not. Inconsistent — collections record changes even when tracking is off.
4. **No `OldItems` / `OldStartingIndex` captured.** Cannot reconstruct deltas for sync/replication.
5. **Reset (Clear) writes a `"{coll}.-1"` garbage key.**

Fix direction: key by entity id (`IUniquelyIdentifiable.Id`) for entity collections, or by a stable synthetic id for value collections; branch on `eventArgs.Action`; gate on `EnableChangeTracking`; record both old and new for Replace/Move.

**C. `Changes` semantics = "last value written", not "diff vs original".**
Setting a property to its original value still records it as changed. Repeated mutations overwrite — only the final value survives. If the intent is "dirty fields vs snapshot", `Entity.SetField` needs to compare against a captured baseline and remove the key when reverting. Currently `Changes.Clear()` is the only baseline reset, and it is entirely manual (see `Program.cs:21`).

**D. No snapshot-on-first-set; relying on `EnableChangeTracking` + manual `Clear()` is fragile.**
`Program.cs` shows the required dance:
```csharp
item.Id = ...;
item.EnableChangeTracking = true;
item.Changes.Clear();
```
Any property set before enabling tracking is invisible. Any code path that forgets `Clear()` double-counts. The generator could emit an opt-in `BeginTracking()` partial method that flips the flag and clears the dict atomically, but does not.

**E. Scoped setter double-fires `SetField` → double `PropertyChanged` + double `Changes` write.**
`SourceCodeGenerator.cs:465-471`:
```csharp
SetField(ref this.{itemName}, value.Id);          // writes Changes["X"] = id-Ref, fires PropertyChanged
if (value.Item != null)
    SetField(ref this.{itemName}, value.Item);    // overwrites Changes["X"] = full Ref, fires again
```
Subscribers see two change events for one logical assignment. `Changes["X"]` ends as the full Ref (intermediate id-Ref lost). Minor correctness/perf issue; the first `SetField` is redundant when `value.Item != null`.

**F. Limited-view (DTO) classes have no change tracking.**
Generated `{Class}_{View}` classes emit plain `{get;set;}` auto-properties — no `SetField`, no `INotifyPropertyChanged`, no `Changes`. By design (DTOs), but worth noting: round-tripping through a view loses tracking. Two-way `UpdateParent` writes back to the source entity, which re-triggers tracking there — acceptable.

**G. `Changes` dictionary can grow unbounded.**
No cap, no eviction, no per-key TTL. Long-lived tracked entities with many property churns retain only latest per key (so bounded by property count, not churn count) — actually fine in the current "last value" model. But if extended to history, needs a cap.

### 1.3 Change-detection verdict

Property-level tracking is functional but semantically shallow ("last value while toggle on"). Collection tracking is broken for all non-Add operations and should not be relied on. `[DoNotTrackChanges]` naming is misleading.

## 2. Scope-Removal Correctness

The scoped setter template (`SourceCodeGenerator.cs:449-481`) is lifted from `SecondScopedEntity.SecondScope` and emits:

```csharp
set
{
    if (value != null && !string.IsNullOrWhiteSpace(value.Id))
    {
        if ({itemName} != null && !string.IsNullOrWhiteSpace({itemName}.Id)
            && Scopes.Contains({itemName}.Id) && {itemName}.Id != value.Id)
        {
            Scopes.Remove({itemName}.Id);
        }
        if (!Scopes.Contains(value.Id)) Scopes.Add(value.Id);
        SetField(ref this.{itemName}, value.Id);
        if (value.Item != null) SetField(ref this.{itemName}, value.Item);
        {getSimpleValue(item)}
    }
    else
    {
        if ({itemName} != null && !string.IsNullOrWhiteSpace({itemName}.Id)
            && Scopes.Contains({itemName}.Id))
        {
            Scopes.Remove({itemName}.Id);
            SetField(ref this.{itemName}, string.Empty);
        }
    }
}
```

Compare canonical `MultiscopedEntity.Scope` setter (`MultiscopedEntity.cs`): uses `Scopes.RemoveAll(f => f == base.Scope.Id)` unconditionally, sets `base.Scope = null` in clear branches, and handles `value != null && IsNullOrWhiteSpace(value.Id)` explicitly.

### 2.1 Bugs

**Bug S1 — Clearing leaves a blank-Id Ref, not `null`.**
Else branch does `SetField(ref this.{itemName}, string.Empty)` → produces a `Ref<T>` with `Id == ""` (via implicit string→Ref conversion), not `null`. `MultiscopedEntity.Scope` sets `base.Scope = null`. Divergence: callers checking `item.MainItem == null` after clearing get `false`. Downstream code expecting null will misbehave.

**Bug S2 — Else branch no-ops when `Scopes` is out of sync with the field.**
The guard `&& Scopes.Contains({itemName}.Id)` means: if the field holds an id that is *not* in `Scopes` (drift from manual edit, partial deserialization, or a prior failed add), the clear silently does nothing — field keeps its old id-Ref. Canonical uses `RemoveAll` with no `Contains` guard → always clears. Generator is stricter and leaks on drift.

**Bug S3 — Non-null `value` with blank `Id` is silently dropped.**
When `value != null` but `IsNullOrWhiteSpace(value.Id)`, the outer `if` fails → `else` branch runs, which only inspects `{itemName}` (the *old* field). The new `value` is never assigned. `MultiscopedEntity.Scope` handles this case explicitly:
```csharp
if (string.IsNullOrWhiteSpace(value.Id)) { Scopes.RemoveAll(f => f == base.Scope.Id); base.Scope = null; }
```
Generator data-loss: caller's intent "set to this blank-id Ref" is lost; only the old scope is cleared (and only if S2 guard passes).

**Bug S4 — `Scopes.Remove` removes one occurrence; `RemoveAll` removes all.**
`MultiscopedEntity` uses `RemoveAll`. If `Scopes` (`List<string>`) ever contains duplicate ids (possible since `List<string>` permits dups and the `!Contains` add-guard only prevents re-adding an existing id, not a race), the generator leaves extras. Defensive divergence; low likelihood but real.

**Bug S5 — Double `SetField` double-fires `PropertyChanged`.**
Covered in §1.2 E. Applies to scoped setters specifically.

**Bug S6 — No validation that the target class exposes `Scopes`.**
`IsScoped` is set by `[AddRefToScope]` on *any* member of *any* class (`Scanner.cs:346-349`). The generated setter references `Scopes.Add/Remove/Contains` unconditionally. `Scopes` only exists on `MultiscopedEntity<T>` (and `SecondScopedEntity<...>` via inheritance). On a class extending `ScopedEntity<T>` (single-scope) — or any non-multiscoped base — the generated code **does not compile**. The generator does not validate base-type compatibility. Either enforce `[AddRefToScope]` only on multiscoped-derived classes (emit a diagnostic `SATURN00x` otherwise) or document the constraint loudly.

**Bug S7 — `value.Id` may be read on a `Ref<T>` whose `Item` is null.**
The setter reads `value.Id` and `value.Item` separately. `Ref<T>.Id` is the persisted ref id; `value.Item` is the lazily-loaded entity. The pattern assumes `Id` is populated even when `Item` is not (deferred ref) — correct for `Ref<T>` semantics, but the generator emits this unconditionally for any `[AddRefToScope]` member regardless of whether the member type is `Ref<T>` vs a plain `T` / string. If `[AddRefToScope]` is applied to a non-`Ref` member, `value.Id` / `value.Item` do not exist → compile error. `Scanner.cs` does not type-check the member kind for `IsScoped`.

### 2.2 Scope-removal verdict

The template is a near-copy of `SecondScopedEntity.SecondScope` — which is a *second* scope on an already-multiscoped entity — but is applied generically to any `[AddRefToScope]` member. It diverges from the canonical `MultiscopedEntity.Scope` behavior in three material ways (S1 blank-Ref vs null, S2 Contains-guard leak, S3 blank-id drop) and is unsafe on non-multiscoped bases (S6) and non-`Ref<T>` member types (S7).

### 2.3 Recommended fixes (scoped setter)

1. Mirror `MultiscopedEntity.Scope` structure: split `value != null && IsNullOrWhiteSpace(value.Id)` from `value == null`.
2. Replace `Scopes.Remove(...)` with `Scopes.RemoveAll(id => id == {itemName}.Id)` and drop the `Contains` guard in the clear path.
3. In clear branches, set the field to `null` (or `default`) — not `string.Empty` — to match canonical null semantics. If `Ref<T>` cannot accept null via `SetField` because of the implicit string conversion, assign the backing field directly or use a `ClearItem()`-style helper.
4. Validate `IsScoped` member type is `Ref<T>` and target class derives from `MultiscopedEntity<T>`; emit a diagnostic otherwise (add `SATURN00x`).
5. Collapse the two `SetField` calls into one: prefer `value.Item ?? Ref<T>.FromId(value.Id)` so only one `PropertyChanged` fires and `Changes` records one value.
6. Gate `getSimpleValue` emission on the runAfterSet flags being relevant to scoped members (currently always emits when flags set, which may double-execute).

## 3. Cross-cutting

- `outputAttributes` (`SourceCodeGenerator.cs:386-418`) still has the `// TODO need to fix` string-replace hack (`Replace(",)]", ")]")`) — fragile; will mangle any attribute whose string parameter ends with `,)]`. Worth a real fix (trim trailing comma before closing).
- `outputViewTwoWayMethod` has a `// TODO need to do this at one point` for `OverrideReturnTypeToUseLimitedView` two-way — the override case assigns `parent.X = this.X.Id` (id-only) instead of the full object, which silently degrades two-way sync for overridden-return-type members.
- Generated class declares `: INotifyPropertyChanged` directly (`SourceCodeGenerator.cs:24`) rather than relying on the `Entity` base — redundant but harmless. If the generated class does not derive from `Entity`, `SetField`/`Changes`/`OnPropertyChanged` are undefined → compile error. No validation that the partial class derives from `Entity`.
